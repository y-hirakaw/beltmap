# beltmap の推測層

beltmap は決定論で取れる情報しか集めない。ラベル集計・ファイル走査・API応答は
beltmap 自身が扱い、**そこで埋まらなかった穴だけ**がこの skill に回ってくる。

## 手順

### 1. 依頼を読む

`.beltmap/enrichment-request.json` を読む。無ければ「先に `beltmap scan` を実行してください」と伝えて終わる。

各タスクはこの形をしている。

| フィールド | 意味 |
|---|---|
| `machine_id` | 対象の機械 |
| `source_text` | 根拠となる機械の定義本文。**判断材料はこれだけ** |
| `source_hash` | 根拠のハッシュ。**そのまま回答に転記する** |
| `fields` | 埋めてほしいフィールド |
| `known_labels` | 実在するラベルの一覧 |

### 2. 根拠だけから読み取る

`source_text` に書かれていることだけを根拠にする。**リポジトリを探索したり、
機械名から意味を推し量ったりしない。**名前が `triage` だから仕分けをするはずだ、
という類の補完をしてはならない。beltmap が根拠として渡したのは `source_text` であり、
それ以外を根拠にすると provenance の表示が嘘になる。

読み取るもの:

- `reads` … その機械が**入力として取得する**ラベル
- `writes` … その機械が**付与する**ラベル。外すだけのラベルは含めない
- `summary` … 何をする機械かの一文

### 3. 埋まらないものは埋めない

**これが最も重要な規則である。**

- `source_text` にラベルが1つも出てこないなら、`reads` と `writes` は空配列にする
- 確信が持てないものは含めない。**入れ忘れより、いい加減に入れるほうが害が大きい**
- `known_labels` に無いラベルは絶対に書かない。beltmap 側の検証で弾かれるが、
  弾かれる回答を作ること自体が間違い

beltmap は「不明」を不明として描ける。もっともらしい嘘は描けない。
埋まらない穴を空欄で返すのは失敗ではなく、正しい結果である。

### 4. 回答を書く

`.beltmap/enrichment.json` に書く。

```json
{
  "version": 1,
  "results": [
    {
      "machine_id": "依頼のものをそのまま",
      "source_hash": "依頼のものをそのまま転記",
      "reads": ["ai-process:ready"],
      "writes": ["ai-process:spec-draft"],
      "summary": "一文",
      "trigger_detail": null
    }
  ]
}
```

守ること:

- **JSONファイルとして書く。**コードフェンスで包まない
- `source_hash` は依頼の値をそのまま転記する。**書き換えたり作ったりしない。**
  これは根拠が変わったときに古い推測を無効化するための値であり、辻褄合わせに
  使うと陳腐化の検出が壊れる
- 依頼されていない機械について回答しない
- `summary` は依頼の本文と同じ言語で書く

### 5. 結果を伝える

何件埋めて、何件を空のまま返したかを、理由とともに伝える。
空にした理由(根拠にラベルの記述が無かった等)は、ユーザーが工場の定義を
直す手がかりになるので省略しない。

そのあと `beltmap scan` を再実行すると取り込まれる、と案内する。
